# Standard Store 2.0 — გადაწყვეტილების ანალიტიკის საფუძველი

**პრინციპი:** გავზარდოთ ადამიანისთვის სასარგებლო გადაწყვეტილების მიღების ალბათობა. ანალიტიკა გვასწავლის, სად შევცვალოთ მაღაზია; არ ქმნის მომხმარებლის ინდივიდუალურ პროფილს.

## 1. საზომები

- ძიების ხილული შედეგი (შედეგიანი / შედეგის გარეშე / ფილტრებით ცარიელი) — ერთი კატეგორია თითოეულ დამონტაჟებულ ხილულ ხედზე; ნაჩვენები კორექცია დამოუკიდებელი სიგნალია. ძიების ფრაზის შეცვლა ითვლება მხოლოდ ძიების გვერდიდან შეცვლილი ფრაზით ძიების შედეგებისკენ გადასვლისას. ცალკე ითვლება პირდაპირი შეთავაზებიდან პროდუქტზე/კატეგორიაზე გადასვლა. ძიების ტექსტი არ ინახება.
- პროდუქტის ხედი: დაუდასტურებელი მარაგი, ფასი, ამოწურული პროდუქტი. შენახვა, შედარებაში დამატება, მინიმუმ ორი თავსებადი პროდუქტის შედარების ხედი, განსხვავებების ჩართვა და შედარების შეზღუდვები.
- კალათის, შეკვეთისა და მოთხოვნის ხედები/მოქმედებები: დაუზუსტებელი ფასი, მარაგი, მიწოდება, რაოდენობისა და ფასის ცვლილებები, ფორმის/სერვერის შეცდომები. ხედში განმეორებით წარმოქმნილი იგივე მდგომარეობა ერთხელ ითვლება; მოქმედებები ცალ-ცალკე.
- ნებაყოფლობითი სამპასუხიანი შეფასება ძიების, პროდუქტის და შედარების გვერდზე: კი / ნაწილობრივ / არა. პასუხების რაოდენობა ცალკე ჩანს; პასუხის არარსებობა ნეგატიური შეფასება არ არის. შეფასება არ არის ობიექტურად სწორი გადაწყვეტილების მტკიცებულება.
- ოპერაციული შედეგები: შეკვეთების და მოთხოვნების შექმნის თარიღის მიხედვით, მათი მიმდინარე სტატუსები, გადახდილი გაუქმებულის გარეშე და მოთხოვნის შეკვეთად გარდაქმნა. არსებული ოპერაციული მონაცემები რეჟიმით არ არის მონიშნული; ამიტომ ეს ნაწილი ყველა რეჟიმს მოიცავს. ანონიმურ მოვლენებთან არ იყოფა კონვერსიის გამოსათვლელად.

## 2. უსაფრთხოება და კონფიდენციალურობა

მიგრაცია `0012_decision_counts` ამატებს მხოლოდ აგრეგატების ცხრილს: მაღაზია, რეჟიმი, დღე (Asia/Tbilisi), დახურული ლექსიკონის მოვლენა და რაოდენობა. არ არსებობს ინდივიდუალური მოვლენების ცხრილი, სესიის ID, პროდუქტის ID, ძიების ტექსტი, URL-ის გზა, დროის ზუსტი ნიშნული, IP ან პირადი ინფორმაცია. გადაცემა ხდება same-origin მოთხოვნით, მხოლოდ ფიქსირებული სათაურით, ქუქიების გარეშე და referrer-ის მხოლოდ origin-ით. დათვლა არ არის საჭირო შესყიდვისთვის; შეცდომა მაღაზიას არ აჩერებს. API ამოწმებს origin-ს, მოვლენების ლექსიკონს, DNT/GPC-ს და იყენებს საერთო პროცესის ლიმიტს, არა ვიზიტორის ID-ს. დღიური მაჩვენებელი შემოსაზღვრულია. ეს არ არის ბოტების სრული ფილტრაცია.

კონფიდენციალურობის გვერდზე შესაძლებელია დღიური სტატისტიკის გამორთვა; ადგილობრივ მეხსიერებაში მხოლოდ გამორთვის არჩევანი ინახება. ეს ვრცელდება აღწერის ძველ ანალიტიკაზეც. DNT/GPC და მიუწვდომელი ადგილობრივი საცავი გამორთავს დათვლას. მონაცემთა დამუშავების ტექსტი სამუშაო ვერსიაა.

## 3. ადმინისტრირება

`/admin/analytics`: მხოლოდ ადმინისტრატორი. ბოლო 7/30 კალენდარული დღის შედეგები, საჯარო/საცდელი ანონიმური მონაცემები განცალკევებულია. დღიური დინამიკა და ოპერაციული ნაწილი ცალკე. ნულოვანი ჩანაწერი არ ნიშნავს, რომ ვიზიტი არ ყოფილა. არ ვითვლით უნიკალურ ვიზიტორს, მიტოვებას, ატრიბუციას ან კონვერსიას ამ ანონიმური სიგნალებიდან. არ ვაგროვებთ საძიებო ფრაზებს — კონკრეტული დავალებებისა და ინფორმაციის ხარვეზების გამოვლენა შემდგომ ეტაპზე უნდა დაეფუძნოს წინასწარ განსაზღვრულ ამოცანათა კატეგორიებს და ნებაყოფლობით პასუხებს.

## 4. შემდეგი ნაბიჯი

პირველი რეალური მონაცემების შემდეგ: ამოცანების სტრუქტურა, დახურული მიზეზების კლასიფიკაცია, პროდუქტის ინფორმაციის ნაკლებობის კვლევა, 5–8 ადამიანზე ხარისხობრივი დავალებების ტესტირება. შემდგომ უნდა განისაზღვროს ოპერაციული მონაცემების რეჟიმის მარკირება და სტატისტიკის შენახვის/წაშლის პოლიტიკა. მიმდინარე ცვლილება ვერ ამტკიცებს, რომ UX უკეთესია, მხოლოდ ამ შეფასების საფუძველს ქმნის.

CI: ერთეულის, მონაცემთა ბაზის და რეალური ბრაუზერის ტესტები; დანერგვამდე ბექაპი. პირდაპირი შეკვეთის, შეთავაზებისა და კატალოგის ბიზნესლოგიკა არ იცვლება.
