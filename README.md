# სტანდარტული მაღაზია (tevo-store)

ერთი ბირთვი, რამდენიმე storefront. ამ ეტაპზე მაღაზია კატალოგს ფაილიდან (`data/catalog.json`) კითხულობს, შეკვეთებს კი Postgres-ში ინახავს. ხიდის API მზად რომ იქნება, მონაცემებს იქიდან წამოიღებს, ისე რომ კომპონენტები და გვერდები არ შეიცვლება.

**სტეკი:** Next.js 16 (App Router, Cache Components), TypeScript, Tailwind 4, Noto Sans Georgian (თვითონ ჰოსტინგდება, Google-ზე დამოკიდებული არ არის).

## გაშვება

```bash
npm install
cp .env.example .env
MEDIA_DIR=/path/to/AgroTrade_Legacy_Media npm run media:link   # ფოტოების საქაღალდე (originals/ შიგნით)
npm run dev          # ან: npm run build && npm start
```

## სტრუქტურა

| სად | რა |
|---|---|
| `data/catalog.json`, `data/catalog.schema.json` | კატალოგი და მონაცემთა კონტრაქტი (v1) |
| `src/lib/catalog/source.ts` | **ერთადერთი ადგილი, რომელმაც იცის, საიდან მოდის მონაცემები.** `FileCatalogSource` ახლა მუშაობს, `KhidiCatalogSource` ხიდისთვისაა მომზადებული. გადართვა: `CATALOG_SOURCE=khidi` |
| `src/lib/catalog/index.ts` | ქეშირებული კატალოგი, ინდექსები, ნავიგაცია, კავშირები |
| `src/lib/catalog/filters.ts` | ფილტრები, დალაგება, ძიება (ლათინური ასოებითაც: `motobloki` → მოტობლოკი) |
| `src/config/store.ts` | storefront-ის კონფიგურაცია (`STORE_ID`). ყველაფერი, რაც მაღაზიებს შორის განსხვავდება, აქ წერია |
| `src/app/globals.css` | design tokens. ბრენდის მიცემა = ცვლადების გადაფარვა `[data-store="tevo"]`-ში |
| `src/i18n/ka.ts` | ყველა ტექსტი. ახალი ენის დასამატებლად საკმარისია `en.ts` იგივე გასაღებებით |

## გვერდები

- `/`: კატეგორიები და მოტობლოკები.
- `/catalog/[category]`, `/catalog/[category]/[type]`: სია ფილტრებით. ფილტრების სიას თითოეული ტიპი კატალოგიდანვე იღებს (`product_types[].facets`).
- `/p/[slug]`: პროდუქტის გვერდი: გალერეა, ფასი, მახასიათებლები ჯგუფებად, აღწერა, თავსებადობა, კავშირები (სათადარიგო ნაწილი, დანადგარი, სახარჯი, ვარიანტი).
- `/search?q=`: ძიება (სახელით, მოდელით, კოდით, ბრენდით).

## რევიუს რეჟიმი

`REVIEW_MODE=1`. ბარათებზე ჩანს ხარისხის ქულა, პროდუქტის გვერდზე კი პრობლემების სია, ძველი სახელი და ძველი ID. ეს რეჟიმი ლიკასთვისაა; საჯარო ვერსიაში გამორთულია და გვერდები `noindex`-ია.

## შეკვეთები და გადახდა

```
კალათა (ბრაუზერში) → /checkout → createOrder() → ბანკი (ან სატესტო ბანკი) → callback → /order/[ნომერი]?t=…
                                       └→ ბაზა: orders, order_items, order_events, payments
```

- **ფასს მხოლოდ სერვერი ადგენს** (`src/lib/orders/quote.ts`). კალათა ბრაუზერში მხოლოდ რაოდენობას ინახავს. თუ ფასი შეიცვალა ან პროდუქტი გაქრა, მყიდველი ამას შეკვეთამდე ხედავს.
- **ფული ინახება მთელ რიცხვად, თეთრებში** (1 ₾ = 100), რომ დამრგვალების შეცდომები გამოირიცხოს.
- **სტატუსები** (`src/lib/orders/status.ts`): `pending_payment → new → confirmed → ready_for_pickup / shipped → completed`, ნებისმიერი ღია სტატუსიდან `cancelled`-ზე გადასვლაც შეიძლება. გადახდის სტატუსი ცალკე ველია (`paymentStatus`).
- **გადახდის პროვაიდერი** (`src/lib/payments/`): ერთი ინტერფეისი. `PAYMENTS_MODE=test` ჩართავს სატესტო ბანკს (`/pay/mock/…`). BOG/TBC-ის კლასები მზადაა, მაგრამ ჯერ ცარიელია. თითო მაღაზიას საკუთარი merchant აქვს: `BOG_CLIENT_ID_<STORE>` და ა.შ.
- **callback** (`/api/payments/[provider]/callback`) იდემპოტენტურია: ბანკმა რომ ორჯერ დარეკოს, დასრულებული გადახდა მაინც არ შეიცვლება.
- **შეკვეთის გვერდი** მხოლოდ საიდუმლო ბმულით (`?t=`) იხსნება. შეკვეთის ნომრის გამოცნობით სხვისი შეკვეთის ნახვა შეუძლებელია.
- **ადმინი**: `/admin` (`ADMIN_PASSWORD`, ხელმოწერილი cookie). აქ არის შეკვეთების სია, ფილტრი, ძიება, სტატუსის შეცვლა, შენიშვნები და ისტორია.
- **ხიდის outbox**: `GET /api/outbox/orders` აბრუნებს ახალ შეკვეთებს, `POST {"ids":[…]}` კი მათ მიღებას ადასტურებს. ავტორიზაცია: `Bearer $OUTBOX_TOKEN`.

## შეტყობინებები (SMS + ელფოსტა)

```
მოვლენა (შეკვეთა / გადახდა / სტატუსი) → templates.ts → notifications ცხრილი (რიგი) → after() → SMS / ელფოსტა
                                                                   └→ /api/cron/notifications (ხელახალი ცდა)
```

- **რიგი ბაზაშია** (`notifications`): შეტყობინება ჯერ ბაზაში იწერება და მხოლოდ შემდეგ იგზავნება, პასუხის გაცემის შემდეგ (`after()`). ნელი SMS სერვისი checkout-ს ვერ შეანელებს, ხოლო შეტყობინების შეცდომა შეკვეთას ვერ გააფუჭებს.
- **დუბლიკატები გამორიცხულია:** თითო შეკვეთაზე, მოვლენაზე, არხსა და მიმღებზე მხოლოდ ერთი შეტყობინება იგზავნება, ბანკი რომ ორჯერ დარეკოს, მაინც.
- **ხელახალი ცდა:** 1, 5, 30, 120 და 720 წუთის შემდეგ, სულ 6 ცდა. სერვერზე cron-ში ჩაწერეთ:
  `* * * * * curl -fsS -X POST -H "Authorization: Bearer $CRON_TOKEN" https://tevo.ge/api/cron/notifications`
- **დაგვიანებული „გადახდა ვერ შესრულდა“** აღარ გაიგზავნება, თუ მყიდველმა უკვე გადაიხადა.
- **მყიდველი SMS-ს იღებს**, როცა შეკვეთა მიღებულია (ადგილზე გადახდისას), გადახდილია, გადახდა ვერ შესრულდა, ან შეკვეთა დადასტურდა, მზადაა გასატანად, გამოგზავნილია ან გაუქმდა. „დასრულებულზე“ SMS არ იგზავნება. თუ მყიდველმა ელფოსტა მიუთითა, იგივე მოვლენებზე HTML წერილსაც იღებს.
- **პერსონალი** (`STAFF_EMAILS`, `STAFF_PHONES`) ყოველ ახალ შეკვეთაზე იღებს წერილს სრული დეტალებით და ადმინის ბმულით.
- **SMS-ში მოკლე ბმულია** (`tevo.ge/o/Ab3dE9xQ`), რომელიც შეკვეთის პირად გვერდზე გადაჰყავს.
- **პროვაიდერები:** SMS — `smsoffice` (smsoffice.ge, API v2, `urgent=true`); ელფოსტა — ნებისმიერი SMTP (Purelymail: `smtp.purelymail.com:465`). ლოკალურად ორივე `console`-ზეა და მხოლოდ ლოგში იწერება.
- **SMS-ის ღირებულება:** ქართული ასოებით SMS UCS-2-ია (70 სიმბოლო ერთ ნაწილში), ამიტომ ჩვენი ტექსტები 2 ნაწილად იგზავნება. `SMS_ALPHABET=latin` ტექსტს ლათინურად გადაწერს (160 სიმბოლო, 1 ნაწილი, უფრო იაფი).
- **ადმინში** შეკვეთის გვერდზე ჩანს ყველა შეტყობინება, მისი სტატუსით და შეცდომით, თუ ასეთი იყო.

## იურიდიული გვერდები

`/info/terms`, `/info/delivery`, `/info/returns`, `/info/warranty`, `/info/privacy`, `/info/contact`. ბმულები footer-შია.

- **ტექსტები** `src/content/legal.ts`-შია და ეყრდნობა „მომხმარებლის უფლებების დაცვის შესახებ“ (2022) და „პერსონალურ მონაცემთა დაცვის შესახებ“ (2023) კანონებს. მონაცემთა დაცვის ზედამხედველი 2026 წლის 2 მარტიდან სახელმწიფო აუდიტის სამსახურია.
- **გამყიდველის მონაცემები** (იურიდიული სახელი, ს/კ, მისამართები, ტელეფონი, ელფოსტა) `src/config/store.ts`-შია, თითო მაღაზიაზე ცალკე. სანამ შევსებული არ არის, გვერდზე „[შესავსებია: …]“ ჩანს.
- **`legalReviewed: false`** გვერდებზე აჩვენებს შენიშვნას „სამუშაო ვერსია“. იურისტის განხილვის შემდეგ ჩართეთ `true`.
- **checkout-ზე** თანხმობა სავალდებულოა. შეკვეთაზე ინახება წესების ვერსია (`termsVersion`) და თანხმობის დრო.

### ბაზა

- ლოკალურად `DATABASE_URL=pglite:./.data/db`: ჩაშენებული Postgres, ინსტალაცია არ სჭირდება, მიგრაციები თავისით ეშვება.
- სერვერზე `DATABASE_URL=postgres://…`, შემდეგ `npm run db:migrate`.
- სქემის შეცვლის შემდეგ: `npm run db:generate` (ახალი SQL ფაილი `drizzle/` საქაღალდეში).

### შემოწმება

```bash
npm run build && npm start   # ცალკე ტერმინალში
BASE_URL=http://localhost:3000 ADMIN_PASSWORD=… OUTBOX_TOKEN=… npm run test:e2e
```

e2e სკრიპტი მთელ ნაკადს გადის: კალათა, ვალიდაცია და თანხმობა, ბანკის უარი, ხელახალი გადახდა, ადგილზე გადახდა, ადმინი, outbox და განმეორებითი callback. შეტყობინებების შესამოწმებლად ჯერ ცალკე ტერმინალში გაუშვით სატესტო SMS/SMTP სერვერი (`SMS_FAIL_CALL=2 npm run test:mocks`), სერვერი კი გაუშვით `.env.test`-ის მსგავსი პარამეტრებით და `MOCK_LOG_URL=http://localhost:3901/_log`-ით. სულ 27 შემოწმებაა.

## ჯერ არ არის

- ნამდვილი BOG/TBC ინტეგრაცია (სჭირდება sandbox წვდომა)
- გამყიდველის იურიდიული და საკონტაქტო მონაცემები (`store.ts`) და ტექსტების იურისტთან განხილვა
- smsoffice.ge-ზე გამგზავნის სახელის (sender) რეგისტრაცია და API გასაღები
- ხიდის adapter
- ადმინის შესვლის მცდელობების შეზღუდვა (rate limit) — production-მდე უნდა დაემატოს

ცნობილი შეზღუდვა: არარსებული პროდუქტის URL `noindex`-იან „ვერ მოიძებნა“ გვერდს აჩვენებს, მაგრამ სტატუსი 200-ია და არა 404. SEO-ს ეტაპზე `proxy.ts`-ით გასწორდება.
